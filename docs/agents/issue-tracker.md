# Issue tracker: GitHub

_Template maintenance: this file serves the development of the Template itself. Delete it in a generated Map project (see the Template maintenance section of `AGENTS.md`)._

Issues and specs for this repo live as GitHub issues. Use the `gh` CLI for all operations.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --comments`, filtering comments by `jq` and also fetching labels.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue close <number> --comment "..."`
- **Claim an issue**: `gh issue edit <number> --add-assignee @me`, before any work on it and before any other write; release it with `--remove-assignee @me` (see "Claim").

Infer the repo from `git remote -v`; `gh` does this automatically when run inside a clone.

## Where issues live

- **The Template** (build pipeline, starter, its CI and docs): this repo, `phmilk/reforged-ts-template`. Its issues moved here from the library on 2026-09-25; the old numbers there redirect here.
- **The library, the Typings, the harness and the lint plugin**: `phmilk/reforged-ts`, which also holds the wayfinder maps, the ADRs the Template follows (the Claim protocol is its ADR 0016, amended for Specs by its ADR 0023), the coverage check `pnpm spec:check` and the reusable `claim-check.yml` workflow that this repository's `claim.yml` calls.
- Refer to an issue in the other repo with its full form, `phmilk/reforged-ts#46`; a bare `#12` means this repo. Sub-issues and "blocked by" edges work across the two repos.

## Claim

A Claim marks an issue as taken by one login: it is held while that login is among the issue's assignees. It binds every Collaborator (a person with push access to this repository or the library's) and every Agent a Collaborator runs: an Agent writes as the Collaborator's login, so its Claim is the Collaborator's. The assignee is the source; the board (below) is a view of it. A Spec has no Claim of its own: its Tickets are claimed, and its assignees are the logins that hold or delivered them ([ADR 0023](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0023-a-spec-carries-every-login-on-its-tickets-and-the-last-tickets-merger-closes-it.md)). The rules are the library's ([Claim](https://github.com/phmilk/reforged-ts/blob/master/docs/agents/issue-tracker.md#claim)), which also draws an issue's life from its creation to its close.

- **First write.** Before working on an issue, assign yourself: `gh issue edit <n> --add-assignee @me`, before the branch, the first commit, any comment and the pull request; a Ticket, with its Spec in the same command ("A Spec's assignees" below). Read the issue back: if a Ticket or an issue outside a Spec now has two assignees, the later one withdraws (`--remove-assignee @me`) and says so in a comment.
- **Claimable.** An open issue with no assignee that is `ready-for-agent` or `ready-for-human`, a Ticket on its Spec's Frontier, or a ticket of a wayfinder map on its frontier (no open blocker). Not claimable: `needs-triage` and `needs-info` (triaged, not claimed), a map, and a Spec, which has no Claim of its own. An unsplit Spec (`needs-split`, no Ticket yet) is not worked at all, whole or in part: it is split first, with `split-spec`, and its Tickets are claimed once they exist ([ADR 0025](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0025-only-a-split-specs-unblocked-tickets-are-worked.md)). Triage and splitting are not claimed: their writes are the brief, the labels and the new issues; whoever implements claims. A bug you find and fix at once: open the issue and claim it in one gesture.
- **One login per issue**, for a Ticket and for an issue outside a Spec. One assigned to another login is theirs: do not add yourself, do not post a brief on it, do not open a pull request that closes it. A second assignee is added only by the first, for pairing; any other two assignees are a conflict to resolve, not work in pair. A Spec is the exception: it carries every login on its Tickets.
- **One Claim at a time**: one issue, or Tickets of one Spec. A Claim means working now, not a reservation: say what you will take next in a comment, and let the native blocked-by order the Tickets. A Ticket is claimed when its work starts, Frontier by Frontier, never ahead; whoever runs `implement-spec` claims every free Ticket of the Spec at once, since its one pull request delivers them: `gh issue edit <ticket>... <spec> --add-assignee @me`. A Ticket already assigned to another login stays theirs.
- **A Spec's assignees.** A Spec's assignees are every login that holds or delivered one of its Tickets, and nothing more: an assignee on a Spec claims none of it. Claiming a Ticket is one command over the Ticket and its Spec, `gh issue edit <ticket> <spec> --add-assignee @me`; the Spec is joined only with a Ticket. `gh issue edit` takes the issues of one repository only, so for a Ticket and its Spec in different repositories (a Ticket here of a Spec in the library), the two commands go on one line, by their URLs: `gh issue edit <ticket-url> --add-assignee @me && gh issue edit <spec-url> --add-assignee @me`. A login that delivered a Ticket stays on the Spec until it closes; a login leaves the Spec only when it releases a Ticket without having delivered any, and holds no other Ticket of it.
- **Splitting a Spec.** A Spec is split into Tickets with `split-spec`, which writes its Coverage table into the Spec's body. The coverage rule (every item of the Spec reaches a Ticket and a criterion) and the table's format are the library's: [A Spec's coverage](https://github.com/phmilk/reforged-ts/blob/master/docs/agents/issue-tracker.md#a-specs-coverage), from [ADR 0023](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0023-a-spec-carries-every-login-on-its-tickets-and-the-last-tickets-merger-closes-it.md).
- **Created without an assignee.** An issue created by `to-spec`, `write-spec`, `split-spec`, triage or an issue form has no assignee; whoever starts it claims it then, and a Spec gets its assignees from its Tickets.
- **A pull request names the Tickets it delivers**, and the issues, and never the Spec, so that no keyword closes a Spec past the coverage check. A pull request of `implement-spec` too: drop the Spec from the keywords it writes. A Ticket the pull request does not deliver stays claimed by the same login until done, or is released.
- **Closing a Spec.** Whoever merges a Spec's last open Ticket runs the coverage check in a clone of the library, `pnpm spec:check <spec> phmilk/reforged-ts-template` for a Spec of this repository and `pnpm spec:check <spec>` for one of the library's, which reads the Spec and its Tickets in both repositories and prints every gap, or none. On green (exit 0), they close the Spec with a comment saying the check is green: `gh issue close <spec> --comment "..."`. On red (exit 1), they comment the gaps it lists on the Spec and leave it open; whoever fills a gap runs the check again. Any assignee of the Spec, or the maintainer, may close it, on a green check.
- **Stale.** A Claim of a Ticket or of an issue outside a Spec is stale after 3 days without a commit on its pull request and without a comment on the issue or the pull request: a draft opened before any work keeps nothing alive. A Spec is never stale; its Tickets are. Any Collaborator may take a stale Claim over: comment first (what and why), then `gh issue edit <n> --remove-assignee <login> --add-assignee @me`, and for a Ticket, join its Spec as when claiming it, while the login taken over leaves it as on a release; the abandoned branch and draft are yours to reuse or drop. The maintainer may reassign at any time.
- **Release.** Leaving an issue you will not finish: comment, then `gh issue edit <n> --remove-assignee @me`. A Ticket released without having delivered any Ticket of its Spec, and with no other held, leaves the Spec in the same command, `gh issue edit <ticket> <spec> --remove-assignee @me`, or in two on one line when they live in different repositories.
- **Stopping.** Leaving a claimed issue open (a question for a human, red CI, a check only a human can make): comment what is pending and where the branch and the pull request stand. The comment keeps the Claim fresh and tells the next session what to resume.
- **The check.** The `claim` workflow (the check `claim / check`) runs on every pull request when it is opened, edited and pushed, drafts included, and reads the issues of this repository it closes: an unclaimed one is assigned to the author, with a reminder that the Claim comes first; one claimed by another login fails the check, whose comment names the takeover path. Two more fail it ([ADR 0025](https://github.com/phmilk/reforged-ts/blob/master/docs/adr/0025-only-a-split-specs-unblocked-tickets-are-worked.md)), each with its own comment: an issue labelled `spec`, since a pull request names the Tickets it delivers and never their Spec; and an issue with an open blocker, of either repository, that the same pull request does not close too, the comment naming each one to deliver first or with it. A pull request of `implement-spec` that closes a Ticket together with its blockers passes. The author of a pull request that closes a Ticket joins its Spec ("A Spec's assignees"): when missing from a Spec of this repository, they are assigned to it, with a reminder that the Spec is joined in the command that claims the Ticket; a Spec in the library is out of the check's reach, since its token writes only in the repository it runs in, so it comments on the Ticket the command that joins it, rewritten once the author is on the Spec, and the one-command Claim stays the main path. A Ticket of this repository it closes whose body still has an unchecked criterion, or a "check whether…" without its `Outcome:` line, draws one comment on the pull request listing them, settled once none is left; it never fails the check, since checking a box is whoever delivers saying the criterion holds. On an assignment, a second assignee not added by the first or by the maintainer, and an open pull request by a login outside the assignees, draw a comment on the issue; adding to a Spec a login that holds or delivered one of its Tickets is no conflict, while adding one that holds or delivered none of them is. A Claim made too early draws a comment too: any assignee on an unsplit Spec (no Ticket yet), or on an issue with an open blocker; the Claim stays, and the comment says it settled once the Claim is no longer premature. The check never reverts anything; the ruleset requires it, so a red check blocks the merge. Bots and pull requests that close no issue are outside it.
- **The board.** [The board](https://github.com/users/phmilk/projects/5) over both repositories shows every open issue with a Status derived from GitHub state (Backlog, Ready, Blocked, In progress at an assignee, In review at an open non-draft pull request, Done), written by one reconcile in `phmilk/reforged-ts`; nobody moves a card by hand. Nothing in the protocol requires reading it: the assignee is the source.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents:

- **Read a PR**: `gh pr view <number> --comments` and `gh pr diff <number>` for the diff.
- **List external PRs for triage**: `gh pr list --state open --json number,title,body,labels,author,authorAssociation,comments` then keep only `authorAssociation` of `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, or `NONE` (drop `OWNER`/`MEMBER`/`COLLABORATOR`).
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either: resolve with `gh pr view 42` and fall back to `gh issue view 42`.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Run `gh issue view <number> --comments`, and read its assignees: an assigned Ticket or issue is taken, whatever its labels, and a Spec carries the logins of its Tickets. Claim it before working on it (see "Claim").
